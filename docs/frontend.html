SmashTourney — Frontend

Routes, guards, services, and how screens decide what to show.

Stack

React 19 rendered by Vite 6, routed with React Router 7. Styling is Tailwind CSS 4 through @tailwindcss/vite, with shadcn-style primitives built on Radix and class-variance-authority. Realtime uses @microsoft/signalr. ESLint runs inside the dev server via vite-plugin-eslint, so lint errors surface while developing rather than only in CI.

Guards and shared state

RequireAuth

Wraps the tournament routes as a layout route and keeps unauthenticated visitors out.

GameSessionGuard

Mounted above the router outlet, so it observes every navigation. Keeps a player from wandering out of an active game by accident.

GameDataProvider / GameIdContext

Wraps the whole app and carries the active game id and player data across routes, with GameDataContext.ts holding the context object and useGameData the accessor hook.

Services

All under src/services/. This is where API and realtime contracts are centralized.

Module Responsibility
RequestService.ts Single typed entry point for HTTP. Routes are named keys with metadata, so call sites pass "getFlowState" and route params rather than assembling URLs.
PersistentConnection.ts SignalR lifecycle — connect, join the game group, subscribe to hub events.
gameFlowService.ts Composes the per-screen fetches. Exposes BracketViewData and InMatchViewData, and returns null on state fetch failure rather than throwing, so a transient error does not unmount a live screen.
inMatchRouting.ts Decides whether a client belongs in the match view or back on the bracket.
matchVoteFeedback.ts Maps each SubmitMatchVoteStatus to a deterministic UI action.
playerSetupService.ts Normalizes player and character selection payloads before submission.
validationService.ts Client-side input rules, rejecting malformed input before it reaches the API.
drawService.ts Geometry helpers for bracket rendering.

Models

src/models/ mirrors the API's shapes in TypeScript: entities/Bracket.ts carries the snapshot, current-match and game-state response types; entities/Player.ts, ApplicationUser.ts and SessionIdentity.ts cover identity and participants. The full Smash Ultimate roster is modelled twice — once server-side under tourneyAPI/Models/Entities/Characters/ and once client-side under src/models/entities/Characters/ — with enums for CharacterId, CharacterName, Archetype, WeightClass, FallSpeed and TierPlacement. lib/loadCharacterCatalog.ts assembles the catalog for use in the UI.

Styling

src/index.css is the only stylesheet the application loads. It is the Tailwind 4 entry point and defines the oklch design tokens for light and dark, plus the fixed Smash background image and the Arial base font. Everything else is Tailwind utility classes in the components.

The shared page frame lives in src/components/PageShell.tsx — the centered translucent panel every screen sits inside, which also owns the page <title>. It was previously duplicated verbatim across eleven files.

src/assets/rawMarkup/ is not part of the running app. It holds static design mockups — HomePage.html, signup.html, Ongoing.html and others — alongside TourneyStyles.css, a hand-written bracket stylesheet with a hardcoded #222/#ddd/red palette. Nothing imports any of it, so its palette never reaches a user. Worth knowing before treating it as live styling to reconcile.

How a screen decides what to show

No screen infers progression on its own. Each fetches GetFlowState and routes on the GameState it gets back, with SignalR events prompting an earlier refetch than polling alone would.

  • LOBBY_WAITING → /lobby/:gameId
  • BRACKET_VIEW → /showBracket/:gameId
  • IN_MATCH_ACTIVE → /inMatch/:gameId or /showBracket/:gameId
  • COMPLETE → results

IN_MATCH_ACTIVE is the one state that splits by viewer: the two participants named in the current match go to the voting screen, and everyone else stays on the bracket. That decision lives in inMatchRouting.ts, and every destination is built by gameRoutes.ts so no screen can construct a path that has lost the game id.

Getting back in after a drop

Phones drop. A backgrounded tab gets reclaimed, the browser is closed by accident, the network goes. All of that clears sessionStorage, which is where the session lives, so anything held only there is gone. Two things survive: the identity cookie, which is HttpOnly and outlives the tab, and whatever is in the URL.

That is why the game screens carry :gameId. GameRouteGuard wraps all three, reads the id from the path, and asks GetPlayerSession/{gameId} who the signed-in user is in that game. Nothing is taken from the client, so a returning player cannot come back as somebody else or claim to be the host. The screen underneath renders only once the answer is in, so no page has to cope with a half-restored session.

  • Session already loaded → render immediately
  • Server resolves the player → restore identity, host flag, and state, then render
  • 404, meaning not a participant → /joinTourney with the code prefilled
  • Request failed → a reconnect message, not a redirect that would lose the URL

Sign-in participates in this too. RequireAuth attaches the attempted path as a next parameter instead of discarding it, and HomePage returns the player there after they sign in — so a lapsed session costs a login, not the tournament. Only same-site absolute paths are accepted back, which returnPath.ts enforces.
