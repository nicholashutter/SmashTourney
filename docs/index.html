SmashTourney — System Overview

A Super Smash Bros. Ultimate themed double elimination bracket tracker, written in C# and React.

Overview API Frontend Testing

What it is

SmashTourney runs tournament brackets for a room of people playing Smash Ultimate together. It works the way a Jackbox party game does: one screen shows the bracket, and everyone else joins from their phone browser and interacts from there. The API is the system of record for tournament progression; the React client renders whatever state the API reports.

Backend

ASP.NET Core minimal API on net8.0, EF Core over SQLite, ASP.NET Identity for accounts, SignalR for realtime, Serilog for structured logs.

Frontend

React 19 with React Router 7, built by Vite 6. Tailwind CSS 4 with shadcn-style UI primitives, @microsoft/signalr for the realtime client, Vitest for tests.

Tests

xUnit v3 integration tests against a real host in ApiTests/, and Vitest suites in tourneyClient/tests/.

How a tournament progresses

The API owns one authoritative GameState per game, and the client routes on it rather than tracking progression itself. That single value is what keeps a phone that missed a realtime event from drifting out of sync.

  • LOBBY_WAITING
  • BRACKET_VIEW
  • IN_MATCH_ACTIVE
  • COMPLETE
  1. A user signs in or registers.
  2. A host creates a tournament and picks single or double elimination.
  3. Players join by game id and gather in the lobby.
  4. The host starts the game; the bracket is generated and broadcast.
  5. The two participants of the active match each vote for the winner.
  6. On agreement the result commits and the bracket advances to the next match.
  7. Play repeats until the game reaches COMPLETE.

Match voting

Progression is driven by participant consensus rather than a host clicking through rounds. Both participants in the active match submit a vote; the result commits only when they agree. Every other outcome is enumerated rather than left implicit, which is what lets the client give deterministic feedback.

Status Meaning
PENDINGVote accepted, still waiting on the other participant.
COMMITTEDBoth participants agreed; the winner is recorded and the bracket advanced.
DUPLICATE_VOTEThis voter already voted on this match.
CONFLICTParticipants disagreed on the winner.
MATCH_NOT_ACTIVEThe match is not the one currently in progress.
INVALID_WINNERThe named winner is not a participant of that match.
VOTER_NOT_PARTICIPANTThe caller is not one of the two players in the match.
GAME_NOT_FOUNDNo game exists for the supplied id.
BRACKET_NOT_STARTEDThe game has not been started yet.
APPLY_FAILEDThe vote was valid but the bracket refused the transition.

Bracket model

Two engines implement IBracketEngine: SingleEliminationEngine and DoubleEliminationEngine. Matches carry a lane, so a double-elimination bracket can describe its losers path and both grand final games in the same snapshot shape a single-elimination bracket uses.

Lanes

WINNERS, LOSERS, GRAND_FINALS, GRAND_FINALS_RESET

Match status

PENDING, READY, IN_PROGRESS, COMPLETE

Modes

SINGLE_ELIMINATION, DOUBLE_ELIMINATION

Odd player counts are handled with byes. A reserved bye id (00000000-0000-0000-0000-000000000000, AppConstants.ByeUserId) stands in for the absent opponent, and bye-involved matches resolve on the server so the client never asks a human to vote on a match with only one real player in it.

Realtime and recovery

SignalR carries a small number of events over the hub at /hubs/GameServiceHub. Connections join a group named for the game id, and broadcasts are scoped to that group.

Direction Name Purpose
Server → callerSuccessfully JoinedAcknowledges the initial connection.
Client → serverJoinGameGroupSubscribes the connection to one game's group.
Client → serverUpdatePlayersAsks the server to rebroadcast the player list.
Server → groupPlayersUpdatedCarries the current player list to the lobby.
Server → groupGameStartedSignals that the bracket has been generated.

Realtime is an accelerator, not the source of truth. Every screen can also reach its state by polling GetFlowState, GetBracket and GetCurrentMatch. A dropped event costs responsiveness, not correctness.

Running it locally

The API binds http://localhost:5280 and expects the client on http://localhost:5173.

# API, without the dummy user seed (default)
dotnet run --project tourneyAPI

# API, with dummy01..dummy16 seeded for multi-player testing
dotnet run --project tourneyAPI --launch-profile http-dummy-users

# Client
cd tourneyClient
npm install
npm run dev

In Development the API seeds a demo identity (demoUser / DemoP@ssword123!) and exposes it at /users/demo-credentials, which the home page uses to offer a one-click sign-in. The dummy seed is governed by DevelopmentSeed:EnableDummyUsers and defaults to false; when disabled, startup removes any previously seeded dummy users so the mode switch stays deterministic between runs.
