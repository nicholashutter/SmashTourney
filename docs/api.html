Composition

Program.cs builds a minimal API host and maps three routers plus the built-in identity endpoints. Service lifetimes are deliberate and worth knowing before changing them.

Registration Lifetime Note
IGameService → GameService Singleton Holds live bracket and vote-ledger state for every in-flight game.
IPlayerManager → PlayerManager Scoped Per-request player persistence.
IUserManager → UserManager Scoped Per-request user operations.
ApplicationDbContext Scoped EF Core over SQLite.
IEmailSender → SmtpEmailSender or LoggedEmailSender Transient Chosen from configuration: SMTP when Email:Smtp:Host and Email:FromAddress are both set, otherwise a sender that writes the link to the log and warns that nothing was posted. Registered for both the generic and non-generic IEmailSender.

Enums serialize as strings via JsonStringEnumConverter, so clients see "LOBBY_WAITING" rather than an ordinal. CORS allows any localhost or 127.0.0.1 origin in Development and only AppConstants.ClientUrl otherwise, with credentials permitted in both cases so the identity cookie flows.

GameService is a singleton, but its bracket state is written through to SQLite. Every change — starting a game, reporting a result, auto-resolving a bye, and a vote still waiting on the other player — is serialized to Game.BracketStateJson before the call returns. HydrateBracketStateAsync reads it back whenever memory is cold, so the in-memory dictionary is a cache and the database is the record. A restarted API resumes a tournament mid-bracket, and mid-vote.

Each game has its own gate, held across read-modify-persist, because every player is on a separate phone hitting the same game at once. What is still single-instance is that gate: it coordinates requests within one process, so running two API instances against one database would need a shared lock rather than this one.

How identity is enforced

Enforcement runs in layers, and the distinction matters because being signed in is the weakest of them. On a host anyone can register against, an authenticated stranger is the caller to design for — not an anonymous one.

  • RequireAuthorization — the group is gated by the authorization middleware. Establishes only that somebody is signed in.
  • Claims check — the handler reads ClaimTypes.NameIdentifier itself and returns 401 when it is absent.
  • Member — the caller must have a player row in this game, or host it. Checked per request against storage, never taken from the client. Failure is 404.
  • Host — the caller's id must match the game's stored HostUserId. A non-member gets 404; a member who simply is not the host gets 403.
  • Open — any signed-in caller, no per-game check.

Non-membership answers 404, not 403. A 403 confirms the game exists, which is the one fact somebody walking game ids is trying to collect. An outsider and a game that was never created are deliberately indistinguishable.

A game id is not a credential. It travels in URLs, gets pasted into chats and read aloud across rooms, so knowing one authorizes nothing on its own. That is why StartGame and EndGame check the host rather than trusting whoever turned up with the id.

Joining is the one action deliberately open to any signed-in caller: that is what a session code is. It rests on a v4 GUID being unguessable, not on the id being secret from people who have it.

Game routes

Mapped by GameRouter under the /Games group.

Method Route Identity Purpose
POST /Games/CreateGameWithMode Claims check Creates a game from CreateGameOptions; returns the new game id and mode. The caller is recorded as host from their claims, never from the body.
GET /Games/GetActiveGames Claims check Lists only the tournaments the caller plays in or hosts. Not a directory of the server — see What the listing does not show below.
POST /Games/GetPlayersInGame/{gameId} Member Returns currentPlayers for the game. 404 to anyone not in it.
POST /Games/AddPlayer/{gameId} Claims check Binds the caller's user id to a Player and adds it to the game. Open to any signed-in caller by design — this is what joining by session code is.
POST /Games/StartGame/{gameId} Host Generates the bracket and broadcasts GameStarted to the game group.
POST /Games/EndGame/{gameId} Host Deletes the game and its players. A game with no recorded host cannot be ended by anyone.
GET /Games/GetBracket/{gameId} Member Returns a BracketSnapshotResponse for rendering.
GET /Games/GetCurrentMatch/{gameId} Member Returns the active CurrentMatchResponse when one exists.
GET /Games/GetFlowState/{gameId} Member Returns the authoritative GameStateResponse the client routes on.
GET /Games/GetPlayerSession/{gameId} Member Rebuilds a returning player's session — their player id, display name, whether they host, and the state their game is in. Everything comes from the game id and the caller's identity cookie, so a phone that lost its tab can get back in. 404 means the caller has no player in that game.
POST /Games/SubmitMatchVote/{gameId} Claims check Records one participant vote and commits the match on consensus. The service additionally requires the voter to be one of the two players in the active match.

User routes

MapIdentityApi<ApplicationUser>() supplies the stock identity endpoints (register, login, refresh, confirmation, password management). UserRouter adds domain endpoints under /users.

Method Route Identity Purpose
POST /users/login Open Signs a user in and establishes the session cookie.
GET /users/demo-credentials Open Development only — returns the seeded demo username and password.
GET /users/session RequireAuthorization Reports the signed-in identity for session validation.
POST /users/logout RequireAuthorization Signs the user out and releases their game association.

Sign-in is intercepted by ConfigureApplicationCookie's OnSignedIn event, which calls AppSetup.HandleUserSession to attach a server-side session record to the user.

Accounts

An address has to be proved before it can sign in. Registration is open to anyone, so without confirmation an account is only a claim: somebody could sign up as another person's address and nothing would ever test whether the mailbox was theirs. Sign-in answers 403 until the address is confirmed, which is a different thing from 401 for a wrong password and the client says different words for each.

This is only enforceable because the mail now actually leaves. The previous sender accepted every message and returned success, so a missing relay was indistinguishable from a working one, and confirmation was a feature the UI implied and the server never performed.

Method Route Identity Purpose
POST /users/register Anonymous Creates an account with a chosen username and address, then emails a confirmation link. If the send fails the account is deleted again, so the address stays free to retry rather than being held by an account that can never be confirmed.
POST /users/login Anonymous Accepts a username or an address. 401 wrong credentials, 403 unconfirmed address, 423 locked out, 429 rate limited.
GET /confirmEmail Anonymous Mapped by MapIdentityApi. The target of the emailed link.
POST /resendConfirmationEmail Anonymous Without this a lost first email leaves an account permanently stuck.
POST /forgotPassword · /resetPassword Anonymous Emails a single-use reset code. An unknown address answers identically to a known one, so the form cannot be used to test who has an account here.

What stops a guess

  • Lockout — five failed attempts, then fifteen minutes, and the correct password is refused too. Sign-in previously passed lockoutOnFailure: false, so a public login form accepted unlimited guesses against any account indefinitely.
  • Rate limiting — ten requests per minute per caller address across the identity surface. Lockout protects one account from many guesses; this protects every account from one password tried across all of them. The bucket is per caller, not global, because a shared bucket would let one flood exhaust everybody's allowance and lock a whole room out of their own tournament.
  • Password length — twelve characters. Length carries more weight than character-class rules, which mostly teach people to end passwords with 1!.

Cookie and transport

The auth cookie is HttpOnly, SameSite=Lax, and Secure everywhere the transport is not deliberately plain HTTP (a developer on localhost, or the in-memory test host). UseHttpsRedirection and HSTS were commented out, which meant the cookie travelled in cleartext and anyone on the same network could read it and become that user; both are on outside Development.

An expired session answers 401 rather than redirecting to a login page that does not exist in an API — otherwise the client sees a 404 where it expected a 401.

Emailed links are HTML-encoded once, not twice. Identity hands confirmation and reset URLs to the sender already encoded. Encoding again turned &code= into &amp;amp;code=, which a mail client resolves such that the code arrives as part of the parameter name — so every resend and reset link failed with a 400. The body builder decodes before encoding, so raw and pre-encoded inputs land in the same place.

What the listing does not show

GetActiveGames briefly returned every game on the server. That is harmless on a laptop at a party and wrong on a public host: it handed any account that completed registration a roll-call of every tournament running, its size, and its state. It now returns only games where the caller has a player row or is the recorded host.

Hosts are included before they take a player slot, because somebody who creates a game and has not joined it yet still has to be able to find it. Membership is read from storage on every request rather than cached, so a player whose row is removed loses access with it.

Discovery does not depend on the listing. Joining happens through a session code or a shared link, which is the model the app is built around — you are given a room rather than going looking through other people's. The client screen is My Tourneys, and its job is getting back into a game after a phone drops.

Being signed in is not an authorization decision. Every check that matters here asks something narrower: are you in this game, do you host it, are you one of the two players in this match. Registration is open, so an authenticated stranger is the ordinary case rather than the exotic one.

Bracket engines

IBracketEngine has two implementations under Services/Brackets/. BracketRuntimeModels.cs holds the mutable runtime state that the read-only view records above are projected from.

SingleEliminationEngine

One lane. A loss eliminates. Byes fill an incomplete first round.

DoubleEliminationEngine

Winners and losers lanes, with GRAND_FINALS and a conditional GRAND_FINALS_RESET when the losers-bracket player takes the first grand final. IsGrandFinalResetRequired on the snapshot reports that condition.

Errors and validation

Utilities/Exceptions/ holds domain exceptions used instead of bare throws, including BracketGenerationException, GameNotFoundException, PlayerNotFoundException, RoundMismatchException, and validation exceptions per entity. Utilities/ModelValidators/ holds GameValidator, PlayerValidator and UserValidator.

Vote handling is the exception to exception-driven flow: SubmitMatchVoteStatus reports refusal as data on a successful response rather than as a thrown error, because refusal is expected traffic — two phones racing the same button is normal, not exceptional.
