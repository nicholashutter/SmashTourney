SmashTourney — Testing

What each suite covers and how to run it.

Overview API Frontend Testing

Running the suites

# API — xUnit v3
dotnet test

# Client — Vitest
cd tourneyClient
npm test

# Client with coverage (v8 provider)
npm test -- --coverage

The API side uses xUnit v3 with Microsoft.AspNetCore.Mvc.Testing, so integration tests run against a real host rather than mocked plumbing. tourneyAPI.csproj declares InternalsVisibleTo("ApiTests"), letting tests reach internal types without widening the public surface for their benefit.

Gaps worth knowing

Authorization is under-tested relative to how it is enforced. Most /Games routes carry no identity check at all (see API → How identity is enforced), so a suite asserting that unauthenticated callers are refused would fail on the current implementation for every route except AddPlayer and SubmitMatchVote. The absence of those assertions is why the gap is not currently visible from a green run.

  • There is no CI workflow in the repository, so the suites are run on demand rather than enforced on push or pull request.
  • GameService is registered as a singleton holding in-memory state; tests that share a host share that state, which is worth keeping in mind when adding suites.
  • Coverage output is written to tourneyClient/coverage/ and CoverageReport/, both gitignored.

Suggested gates before merge

  1. All API tests pass (dotnet test).
  2. All client tests pass (npm test).
  3. Bracket matrices pass for power-of-two and odd player counts, in both elimination modes.
  4. Lint is clean (npm run lint), which the dev server also surfaces inline.
