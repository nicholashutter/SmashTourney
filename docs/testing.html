SmashTourney — Testing

What each suite covers and how to run it.

Overview API Frontend Testing

Running the suites

# API — xUnit v3            → 181 passing
dotnet test ApiTests/ApiTests.csproj

# Client — Vitest           → 173 passing
cd tourneyClient
npx vitest run

# Client typecheck
npx tsc -b --noEmit

# Client with coverage (v8 provider)
npx vitest run --coverage

The API side uses xUnit v3 with Microsoft.AspNetCore.Mvc.Testing, so integration tests run against a real host rather than mocked plumbing. tourneyAPI.csproj declares InternalsVisibleTo("ApiTests"), letting tests reach internal types without widening the public surface for their benefit.

Two invocation traps worth knowing. dotnet test exits 0 when it fails to run anything at all, so piping it through tail or Select-Object and trusting the exit code will report success for a suite that never executed — read the Passed! or Failed! line.

And plain npx tsc --noEmit checks zero files here: tsconfig.json is solution-style, with "files": [] and project references, so only the -b (build mode) form actually typechecks anything. npm run build gets this right because it runs tsc -b.

API suites

Under ApiTests/.

File Covers
CustomWebApplicationBuilder.cs Test host factory. Not a suite — it is the harness the integration tests boot the API through. Swaps in RecordingEmailSender and raises the auth rate limit, which a suite registering hundreds of accounts would otherwise trip.
RecordingEmailSender.cs Captures account email instead of sending it, and resolves HTML entities in links the way a mail client does. This is what makes the auth tests genuinely end to end: no test mints a confirmation token through UserManager, so a registration that stopped sending mail would fail them rather than pass silently.
AuthenticatedClientFactory.cs Builds signed-in clients by walking the whole flow — register, read the emailed link, follow it, sign in. Every suite needing an authenticated caller goes through it, so the confirmation path is exercised constantly rather than once.
AuthEndToEndTest.cs The account lifecycle as a person experiences it: confirmation required before sign-in, a tampered token refused, one account's link not confirming another, lockout after repeated wrong passwords (including refusing the correct one, and not locking bystanders), password reset with single-use codes, resend, and sign-out.
AuthRateLimitTest.cs The limiter, over HTTP. Runs under its own RateLimitTesting environment because Program.cs reads the limit while building the host — before the test factory's configuration callbacks run — so an appsettings file is the only source that arrives in time.
AuthServiceTest.cs Registration, login, logout, and session validation behaviour.
GameAccessControlTest.cs · GameRouteAccessTest.cs That belonging to a game is what grants access to it, at the service layer and over HTTP. Written from the outsider's side — a real account with a real cookie — because that is the caller a signed-in-only check cannot distinguish from a participant.
MultiGameTest.cs Isolation between concurrent tournaments, the games listing, host-only ending, and the stale sweep.
BracketEngineTest.cs Seed order, match counts, progression links, and play-out to a single champion.
SessionResumeTest.cs Rejoining from a game id, and that bracket state, reported results and half-cast votes all survive a restart.
GameRouterTest.cs Route-level behaviour for the /Games group — status codes, payload shapes, and progression through the flow-state endpoint.
GameServiceTest.cs The orchestrator: bracket generation per mode, vote-ledger handling, progression, and bye auto-resolution for odd player counts.
PlayerRepositoryTests.cs Player persistence and retrieval.
UserServiceTest.cs User creation and lookup paths.
RealTimeTest.cs SignalR contract: connecting to the hub, receiving the join acknowledgment, and confirming game-start broadcasts reach every client in the same group.
TestContracts/ Shared request and response shapes used across the API suites.

Gaps worth knowing

Authorization is now tested from the outsider's side. This note previously recorded the opposite: most /Games routes carried no identity check, and no suite asserted that unauthenticated callers were refused, so the gap was invisible from a green run. That is the shape these gaps take — the tests agreed with the code, and both were wrong together.

The lesson worth keeping: a passing suite says the code does what the tests say, not what it should. Every auth check added since is paired with a negative test written from the perspective of a caller who should be refused, and a positive one, because guards that lock out the legitimate user are the usual failure mode.

  • There is no CI workflow in the repository, so the suites are run on demand rather than enforced on push or pull request.
  • GameService is registered as a singleton holding in-memory state; tests that share a host share that state, which is worth keeping in mind when adding suites.
  • Coverage output is written to tourneyClient/coverage/ and CoverageReport/, both gitignored.

Suggested gates before merge

  1. All API tests pass (dotnet test).
  2. All client tests pass (npm test).
  3. Bracket matrices pass for power-of-two and odd player counts, in both elimination modes.
  4. Lint is clean (npm run lint), which the dev server also surfaces inline.
